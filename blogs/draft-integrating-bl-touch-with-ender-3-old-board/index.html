[Draft] Integrating BL Touch (well, actually CR Touch) with Ender 3 Old Board using AI

July 31, 2026 8 min read 15 views

I was fed up with my printer — wherever I moved it, I had to recalibrate it. I came to know a bed leveler is the correct fix for this.

But after purchasing it, I realized it was meant for the newer Ender 3 boards, not mine — mine was purchased back in 2020. And honestly, I don't understand why these product listings never document setup steps for the older boards. Everything online just assumes you have the new silent-board version.

Note: the sensor I actually bought is a CR Touch, not a BL Touch (link to the one I got: CR Touch). They're pin-compatible and treated identically by Marlin, but if you're following along and bought a CR Touch too — same story applies to you.

From here and there, I came to know I'd have to purchase one more piece of hardware just to make this work on an old board — a 27-pin adapter/breakout board, shown below:

Touch or Filament Sensor — Ender 3

This adapter is what actually lets a probe talk to the old v1.1.4 board's 27-pin connector, since the old board doesn't expose a dedicated probe port the way the new silent boards do.

The wiring pain

Wiring it out was another headache, but you can easily find the pinout on the product page itself.

Do note: while pulling wires here and there during this process, you may accidentally disturb the power cable on the board. Keep an eye on that too, otherwise you'll also end up buying a new SMPS like I did.

If Creality doesn't officially sell/support in the country you're residing in, I'd recommend buying an SMPS locally at a cheaper rate and just reusing the front panel/connector part from your old one.

Firmware side — this is where it gets real

Now the work doesn't end with wiring. With the wiring done, we still have to flash firmware onto the Ender 3 board that actually understands the probe. Since this is an old 8-bit ATmega1284P board, you can't just drag-and-drop firmware onto an SD card the way newer boards allow — the old board needs a bootloader burned onto it first, using an Arduino as an ISP programmer, before it'll even accept new firmware.

I used an Arduino (Uno, in my case) wired up as the ISP programmer, the way shown below:

Above Fig Shows Creality 3D V1.1.4

Resources I referred to while figuring this out Burn Bootloader and Firmware on Ender 3 — Instructables CR Touch wiring and config for Ender 3 v1.1.4 — Klipper Discourse 27-Pin Breakout Board for BL Touch — RoboticsDNA YouTube walkthrough The hardware/firmware settings that actually need to change

If your board is old like mine, here's what's genuinely different from the "just flash and go" tutorials aimed at newer boards:

Motherboard identity in Marlin's Configuration.h must be set to the Melzi-based v1.1.4 board (BOARD_MELZI_CREALITY), not the newer silent board define most tutorials assume. Bootloader burn is mandatory first — old boards ship without a bootloader capable of accepting firmware over USB directly, so you need the Arduino-as-ISP step before any firmware upload will work at all. Probe pin assignment must match your physical wiring — since we're going through the 27-pin adapter board, the CR Touch's signal, 5V, and GND lines land on specific header pins on the adapter (labeled SIG, GND, VCC in the photo), and Marlin's Z_MIN_PROBE_PIN / servo pin defines need to match wherever you actually wired it, not the tutorial's assumed pin. Enable BLTOUCH in Configuration.h (CR Touch uses this same flag — Marlin doesn't distinguish between them). Z-Safe-Homing, Bilinear Auto Bed Leveling, and probe offsets all need to be set based on where your probe physically sits relative to the nozzle once mounted. EEPROM settings enabled so your probe offset and leveling mesh actually persist across power cycles instead of resetting every time. The Claude Code prompt I used to actually get through the flashing part

Rather than following the tutorial screen-by-screen and second-guessing every avrdude error myself, I had Claude Code walk me through the whole bootloader burn + Marlin flash process interactively — checking my toolchain, catching wiring mistakes from the actual error output, and stopping before every risky command to get my go-ahead. Sharing it here in case it saves someone else the same headache:

You are acting as an embedded systems assistant running on a host machine (commonly a Raspberry Pi / Linux, but detect the actual OS). Goal: use an Arduino UNO (SMD) as an ISP programmer to burn a bootloader onto a Creality Ender-3 v1.1.4 board (ATmega1284P), then compile and flash Marlin 1.1.x with BLTouch/bed-leveling support (probe hardware already integrated).
Work INTERACTIVELY. After each step STOP and wait for my confirmation before continuing. Verify the result of every command before moving on. Do not dump the whole plan at once.
GUIDING RULE FOR SETUP: every install/config step below is CONDITIONAL. Always CHECK whether something is already installed/configured first, print what you found, and SKIP the install if it's already there. Only install what's missing. Never reinstall or overwrite existing config without asking.
=== PHASE 0: DETECT + VERIFY ENVIRONMENT ===

Detect OS, architecture, and shell. Print them.
Check if arduino-cli is installed (command -v arduino-cli and arduino-cli version).
If installed: print the version and continue.
If NOT installed: install it (official install script or the OS package), then verify.
Check for an arduino-cli config (arduino-cli config dump).
If a config exists: leave it as-is.
If none: run arduino-cli config init.
LINUX ONLY — serial permissions: check if my user is in dialout (groups | grep dialout).
If yes: continue.
If no: instruct me to run sudo usermod -aG dialout $USER and re-login, and do not proceed with serial steps until access works.
Check installed cores (arduino-cli core list):
arduino:avr — if missing, arduino-cli core install arduino:avr.
MightyCore:avr (provides ATmega1284P) — if missing:
ensure this URL is in additional board manager URLs: https://mcudude.github.io/MightyCore/package_MCUdude_MightyCore_index.json
arduino-cli core update-index
arduino-cli core install MightyCore:avr Only install what's absent. Then print the ATmega1284P FQBN.
=== PHASE 1: IDENTIFY THE UNO === 6. Have me connect ONLY the Uno (if not already). Run arduino-cli board list. Identify the port: - Linux: /dev/ttyACM0 (genuine ATmega16U2 USB) or /dev/ttyUSB0 (CH340 clone) - macOS: /dev/cu.usbmodem* or /dev/cu.wchusbserial* - Windows: COMx If nothing appears, diagnose (dmesg | tail, lsusb, or Device Manager) — a CH340 clone may need its driver. Note the exact port for later commands. 7. Upload the built-in ArduinoISP sketch to the Uno (FQBN arduino:avr:uno, the port from step 6). Confirm success. 8. Have me place a 10µF cap between the Uno RESET pin and GND AFTER the ArduinoISP upload (+ leg to RESET). Required to stop the Uno auto-resetting during the burn. Wait for me to confirm it's in place.
=== PHASE 2: WIRING (Uno -> Ender ISP header) === 9. Print an ASCII diagram using Uno pin numbers: Uno D13 -> SCK Uno D12 -> MISO Uno D11 -> MOSI Uno D10 -> Ender RESET Uno 5V -> VCC Uno GND -> GND Explain how to find pin 1 on the Ender 6-pin ISP header (square pad / dot / silkscreen). Warn that the Uno's ICSP block and D11/12/13 are the same SPI lines — use one set only, never both. 10. Recommend how to power during the burn (Uno 5V vs the Ender's own PSU) and explain the safer choice. Warn against back-powering 5V from both sides at once. STOP and have me confirm wiring is done + photographed before any burn.
=== PHASE 3: BURN BOOTLOADER === 11. Show the exact arduino-cli burn-bootloader command (Uno as programmer, target = ATmega1284P FQBN, port from step 6) and explain the fuse settings BEFORE running. Wait for my "go". 12. Parse avrdude output. On failure (signature 0x000000 or mismatch, "not in sync: resp=0x00", stk500 errors, programmer not responding), diagnose from the ACTUAL error text. Common causes: wrong port, missing 10µF cap, dialout perms, ArduinoISP not really uploaded, swapped MISO/MOSI. No blind retries.
=== PHASE 4: BUILD + FLASH MARLIN === 13. Ask where my configured Marlin 1.1.x source is (or help me obtain it). Probe hardware is ALREADY installed — confirm probe type (BLTouch/clone vs inductive) and the EXACT Ender pins I wired the servo/control line and the Z-min line to, so the config matches the wiring. 14. Verify Configuration.h before compiling: MOTHERBOARD = BOARD_MELZI_CREALITY, BLTOUCH, USE_PROBE_FOR_Z_HOMING, Z_SAFE_HOMING, AUTO_BED_LEVELING_BILINEAR, NOZZLE_TO_PROBE_OFFSET, grid points, EEPROM_SETTINGS, correct LCD define. Flag anything inconsistent with the pins I gave. 15. Compile with arduino-cli for the ATmega1284P FQBN. Report and fix errors. 16. Flash: the bootloader is now installed, so flash over the Ender's OWN USB (it enumerates as its own serial node) — the Uno ISP is no longer needed. Re-confirm which port is the Ender, show the command, wait for go, flash, verify.
=== PHASE 5: BRING-UP === 17. Connect over serial (e.g. arduino-cli monitor -p <ender port> -c baudrate=115200) and run in order: M502, M500, M501. Explain each. 18. Guide first tests: G28 auto-home, M48 probe repeatability, then G29. Explain good vs bad output and how to set/save the Z probe offset (M851 then M500).
RULES:

Never run a burn/flash command without showing it and getting my "go".
After every command, check the exit code + actual output; report success/fail explicitly.
Diagnose hardware/driver issues from real evidence (dmesg/lsusb/avrdude text), not guesses.
Every setup action is check-first, install-only-if-missing.
Keep responses tight; expand only when I ask.
Start with PHASE 0, step 1.

If you're on an old Ender 3 board and thinking of adding a CR/BL Touch — budget for the adapter board, budget for a possible spare SMPS if you're clumsy with wires like me, and don't expect a single tutorial to cover your exact board revision end to end. It's a stitch-together job, but it does work.
