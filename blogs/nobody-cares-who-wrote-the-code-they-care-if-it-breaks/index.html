Nobody Cares Who Wrote the Code. They Care If It Breaks.

July 29, 2026 11 min read 6 views

There's an argument happening in every engineering team right now, and most of it is a waste of breath. It goes: should real production code be written by a human or by an AI? People get religious about it. They shouldn't.

Here's the thing production doesn't care about: who typed the code. A payment system doesn't check the author's employment status before it processes a transaction. A database doesn't refuse to corrupt itself out of respect for a human author. Production cares about exactly three things — is the code reliable, is it secure, and is it maintainable. If AI-generated code passes those bars, it ships. If human-written code fails them, it shouldn't. The origin is a distraction.

What has changed is the speed and the blind spots. When you "vibe code" — describing what you want and letting an assistant scaffold it — you can produce a working feature in minutes. But that speed cuts both ways. <cite index="7-1">AI-generated code introduces vulnerabilities at roughly 40% higher rates than hand-written code — not because the AI is careless, but because it confidently reproduces insecure patterns from its training data.</cite> The code looks right, which is precisely the danger. <cite index="2-1">Developers are inclined to trust AI code, which often looks reliable at first glance, and a cursory review can't catch the logic and correctness errors that cause outages in production.</cite>

So the real question isn't who writes it. It's what does the code have to pass before it's allowed to matter? Let me walk you through the guardrails I'd put in place, the way I'd set them up for a team shipping fast.

The mindset shift: you're not a typist anymore, you're a reviewer

When you vibe code, your job changes. You stop being the person who produces each line and become the person who verifies each line. That's not a demotion — reviewing is the harder, more senior skill. A junior engineer writes code; a senior engineer decides whether code is trustworthy.

The mistake teams make is keeping the speed of AI generation but dropping the rigor of review. <cite index="1-1">When AI outputs skip the code review processes and governance controls that traditional development relies on, it creates a compounding problem: organizations ship more code faster with less human oversight.</cite> Speed without a safety net isn't productivity — it's just faster accumulation of debt and risk.

The fix is to move the safety net into the pipeline so it runs automatically, on every change, whether a human or an AI wrote it. Let's go bar by bar.

Bar 1: Reliable — does it do what it's supposed to, every time?

Reliability is about correctness under real conditions, not just "it ran once on my machine." The tools here are old friends — they predate AI — but they matter more now, not less, because AI writes plausible code that can be subtly wrong.

Tests are non-negotiable, and this is where AI actually shines. The single highest-leverage habit in vibe coding: after the assistant writes a feature, have it write the tests too — then read the tests yourself. Tests are easier to review than implementation because they describe intended behavior in plain terms. If a test looks wrong, the feature is wrong. Ask for unit tests on the logic, integration tests on the seams between components, and at least one test for the failure case (what happens on bad input, a timeout, an empty result). An AI will happily write the happy path and forget that networks fail; your job as reviewer is to insist on the unhappy paths.

Type checking catches a whole class of bugs for free. Static type systems — TypeScript, Python type hints with mypy or pyright, Rust's compiler — reject nonsense before it runs. AI-generated code is especially prone to plausible-but-wrong data assumptions (passing a string where an object is expected, assuming a field exists). Types turn those into errors at write time instead of incidents at 3 a.m.

Linters and formatters enforce consistency. Tools like ruff, eslint, and prettier run in milliseconds and catch dead code, unused variables, and stylistic drift. When code across your app follows one consistent shape, reviewers spot the real problems faster because they're not distracted by cosmetic noise.

Put it all in CI. Continuous integration is just the practice of running every one of these checks automatically on every proposed change, before it merges. This is the load-bearing idea of the whole article: the guardrails only work if they're automatic and unavoidable. A check you have to remember to run is a check you'll skip under deadline pressure — and vibe coding is all deadline pressure.

Bar 2: Secure — can it be attacked?

This is the bar AI-generated code fails most often and most quietly, so it deserves the most attention. The vulnerabilities aren't exotic. <cite index="3-1">AI coding assistants introduce the same classic flaws humans do — injection bugs, insecure defaults, and hardcoded credentials — which is exactly why AI-generated code needs the same security scrutiny as anything a person writes.</cite> The problem is volume and inattention: <cite index="7-1">entire features get scaffolded in minutes, and nobody reads the security-sensitive parts before they land in a pull request.</cite>

The tool category that addresses this is SAST — Static Application Security Testing. In plain terms: a SAST tool reads your source code without running it and flags known-dangerous patterns — a database query built by gluing strings together (SQL injection), a secret key committed in plaintext, a weak crypto choice. Think of it as a spell-checker for security mistakes.

A few things worth knowing so you sound like you've actually used these, not just read about them:

  • Scan at the pull request, not at the end. <cite index="3-1">PR-level scanning catches AI-generated vulnerabilities before they're merged — regardless of whether a developer or a coding assistant wrote them.</cite> A scanner that only runs the night before release is a scanner nobody acts on. Catching the issue on the line that introduced it, in the PR, is what makes it fixable.
  • The market splits into three tiers, and knowing this is a genuine signal of fluency. <cite index="3-1">There are legacy rule-based scanners, AI-assisted platforms that bolt machine learning onto older engines, and a newer class of AI-native tools that reason about code rather than just matching patterns.</cite> The distinction matters: <cite index="7-1">a traditional tool tells you "this could be an injection," while an AI-native one tells you "this is an injection, here is a tested fix."</cite>
  • False positives are the silent killer. If a tool cries wolf 200 times a week, developers stop reading it — <cite index="3-1">the result is alert fatigue and wasted time.</cite> The whole game in modern tooling is precision: <cite index="7-1">leaving three targeted comments on the lines that actually introduced risk, instead of a 200-finding report nobody triages.</cite>

On specific tools — and I'd frame these to any interviewer as "the current landscape" rather than personal endorsements, since the space moves fast: <cite index="6-1">a 2026 evaluation rated Checkmarx One, Semgrep Code, and GitHub's CodeQL highest for detection coverage and workflow integration, with Snyk Code strong on real-time IDE scanning and SonarQube offering a free self-hosted option.</cite> A sensible starting stack for a fast-moving team, as one comparison puts it: <cite index="9-1">a fast PR gate like Semgrep or Snyk, a deep scanner like CodeQL, and a governance layer on top for teams generating code at AI velocity.</cite> Many of these now close the loop with autofix — <cite index="7-1">Snyk's agentic fix claims around 80% autofix accuracy, and GitHub's Copilot Autofix ships inside every Advanced Security plan.</cite>

Two more security guardrails that aren't SAST but belong in the same breath:

  • Secret scanning specifically hunts for credentials, API keys, and tokens accidentally committed to the repo. AI assistants are notorious for hardcoding a placeholder key that turns out to be real. Tools like gitleaks or trufflehog block these at commit time.
  • SCA — Software Composition Analysis — checks the dependencies you pulled in, not the code you wrote. <cite index="4-1">SAST analyzes the code your team writes, while SCA finds vulnerabilities in the open-source libraries and third-party packages you depend on.</cite> This matters doubly for AI code, which loves to import a package to solve a problem — sometimes a package that's outdated, abandoned, or (in the worst case) doesn't exist and was hallucinated.

Bar 3: Maintainable — can the next person understand it in six months?

Reliable and secure code that nobody can change is a slow-motion failure. Maintainability is the bar people skip because nothing breaks today — but it's what determines whether your codebase is an asset or a liability a year from now.

Here's the specific trap with AI at scale, and it's worth naming precisely because it's the failure mode traditional tooling wasn't built for: <cite index="9-1">AI coding agents introduce gaps that file-level scanners miss — inconsistent patterns across generated services, and architecture-level risks that don't show up when you scan one file at a time.</cite> Ask an AI to build the same kind of feature three times and you may get three different approaches, three different naming conventions, three different error-handling styles. Each works in isolation. Together they're a maintenance nightmare, because there's no single mental model that explains the whole system.

The guardrails:

  • Enforce one consistent style, mechanically. This is where linters and formatters earn their keep a second time — not for correctness but for uniformity. When every file looks like it was written by the same careful person, the codebase stays legible no matter who or what generated it.
  • Give the AI your conventions up front. Most assistants let you set project-level context — a rules file, a conventions doc, a system prompt that says "we use this pattern, this error style, this folder structure." Feeding your standards in before generation is far cheaper than fixing drift after. Treat it as onboarding a new teammate: you'd tell a human how your team writes code; do the same for the AI.
  • Keep functions small and single-purpose, and demand real names. A reviewer's ability to verify code depends on being able to hold one piece in their head at a time. AI will happily generate a 200-line function that does six things; push back and have it decomposed. Insist on descriptive names over data, temp, and handleStuff.
  • Require the "why," not just the "what." Code shows what it does; comments and commit messages should capture why a non-obvious choice was made. AI is good at explaining its own code if you ask — capture that explanation in the PR description so the next person inherits the reasoning, not just the result.
  • Track code health over time. Platforms like SonarQube score maintainability — complexity, duplication, test coverage — and let you set a quality gate that blocks merges when health drops below a threshold. It turns "maintainability" from a vague virtue into a number the pipeline enforces.

Putting it together: the pipeline is the point

None of these tools is new or magic on its own. What makes them work is wiring them into an automatic gate that every change passes through, so the guardrails don't depend on anyone remembering to be careful. Here's the shape of a sane setup for a team that vibe codes:

  1. In the editor, as code is generated: type checker and linter running live, plus a real-time security scanner catching the obvious stuff before it's even committed.
  2. At commit, on your machine: formatter, secret scanning, and a fast lint pass — cheap checks that stop the worst mistakes from ever leaving your laptop.
  3. At the pull request, automatically: the full test suite, a PR-level SAST gate, dependency (SCA) scanning, and a code-health quality gate. Nothing merges until these pass.
  4. A human reviews with all that noise already filtered out — free to focus on the questions machines can't answer: is this the right approach, does it fit our architecture, does the business logic actually make sense?

Notice what this does to the human-vs-AI debate: it dissolves it. The pipeline applies the same bar to every line regardless of origin. AI-written code that passes is trusted; human-written code that fails is blocked. That's the whole philosophy — judge the code, not the author.

The one thing to remember

Vibe coding didn't lower the bar for production software. It just moved the work. The bottleneck used to be writing code; now it's verifying it. The engineer who thrives in this shift isn't the one who types fastest or the one who refuses to use AI on principle — it's the one who builds the guardrails that let a team move fast and sleep at night.

Reliable, secure, maintainable. Those three words are the entire job now. Set up the pipeline that enforces them automatically, and it genuinely stops mattering whether the code was written by a person or a machine — which is exactly how it should be.
